关键结论

  • 0.6B 服务：吞吐随并发持续爬升，在 C=128 附近趋于平顶（峰值 222.8 samples/s），继续加并发吞吐不再上升，只是排队变长；全程无 HTTP 错误。
  • 4B 服务（短请求）：可以顶到 C=128（335.9 samples/s），短文本下拐点晚于 0.6B。
  • 4B 服务（中等长度文本）是关键风险点：吞吐在 C=32 见顶（256 req/s）后不升反降，C=64 时跌至 113 req/s（-56%），p99 延迟从 145ms 直接跳到 598ms。这不是网络或客户端瓶颈，而是 --gpu-memory-utilization 0.5 限制下 KV cache / batch token 预算触顶导致的调度退化。
  • 错误率不能作为并发上限的判据：vLLM 有排队保护，压到 C=256 依然 0 报错；真正该参考的是 吞吐拐点 + p99 延迟，而非是否报错。
  • 建议：0.6B 服务并发可放到 ~128；4B 服务若业务输入偏长（几百字以上），建议将并发控制在 ~32，或调大 M4B_GPU_UTIL（当前 0.5）为 KV cache 争取更多显存以推迟拐点。
